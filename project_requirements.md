# Automated Medical Certificate System — Project Requirements

## 1. Project Overview

The Automated Medical Certificate System is a web application built for the Nurse Office of Batangas State University Balayan Campus. It replaces the manual, handwritten issuance of medical certificates with a fully digital workflow: applicants fill out an application form, and clinic staff (admin) review every submission, manage the history, and export official certificates as PDF files.

### 1.1. Objectives
* **Speed:** Submit an application and produce a downloadable PDF medical certificate in under 2 minutes.
* **Accuracy:** Structured, validated form inputs eliminate illegible handwriting and data entry mistakes.
* **Security:** Restrict the admin layer behind an 8-digit PIN issued by the system.
* **Auditability:** Keep a complete, searchable history of every application form submitted.

### 1.2. Scope of Work
* **In-Scope:**
  * Client-facing application form (public, no login required).
  * Admin layer: view, search, filter, and manage the full history of applications.
  * PDF export of any application form from the admin layer.
  * 8-digit PIN-based access control for the admin layer.
* **Out-of-Scope:**
  * Integration with external hospital/EHR systems.
  * Patient accounts, password recovery, or OAuth providers.

## 2. Core Concept — Two-Layer Web Application

The system is composed of two distinct layers within a single web application:

```
┌─────────────────────────────────────────────────────────────┐
│                     WEB APPLICATION                         │
│                  (React + Vite + shadcn/ui)                 │
│                                                             │
│  ┌─────────────────────┐      ┌──────────────────────────┐  │
│  │   LAYER 1: CLIENT   │      │   LAYER 2: ADMIN         │  │
│  │                     │      │                          │  │
│  │  Application Form   │ ───▶ │  - View all submissions  │  │
│  │  (requirements are  │ data │  - Full history          │  │
│  │   inputted here)    │      │  - Export to PDF  ★      │  │
│  │                     │      │  - Protected by 8-digit  │  │
│  │  Public / no login  │      │    PIN                    │  │
│  └─────────────────────┘      └──────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

### 2.1. Layer 1 — Client (Application Form)
* The public entry point of the system.
* Applicants (students/employees) fill in the medical certificate requirements through a structured form:
  * Full Name, Student/Employee ID, Course/Department, Contact Number
  * Consultation date, Reason/Reason for consultation
  * Diagnosis, Vital signs, Fit / Unfit status, Recommendations
* Client-side validation with clear inline error messages (shadcn form components).
* On submission, the record is persisted and appears instantly in the admin layer.
* No authentication required — the form is open to intended applicants.

### 2.2. Layer 2 — Admin (History & PDF Export)
* Protected by an **8-digit PIN** generated by the system (see §5 Security).
* Displays **all** application forms ever submitted, with:
  * Sortable, filterable, and searchable history table (by name, ID, date, status).
  * Pagination for large record sets.
  * Detail view of any single application.
* **Kicker feature — PDF Export:** the admin can export **any** application form as a
  professionally formatted PDF medical certificate (single record or bulk export),
  generated directly in the browser for instant download.
* Admin can mark applications as processed/pending and remove invalid entries.

## 3. Technical Requirements

### 3.1. Technology Stack
* **Framework:** React 18+
* **Build Tool:** Vite (fast dev server and optimized production builds)
* **UI Library:** shadcn/ui (Radix primitives + Tailwind CSS + Lucide icons)
* **Routing:** React Router (client routes vs. admin routes)
* **State/Data:** Lightweight client state (Context/hooks) + REST API calls
* **PDF Generation:** Client-side PDF library (e.g. `jspdf` + `html2canvas`, or `react-pdf`)
* **Persistence:** Lightweight backend or local storage adapter behind a thin API layer
  (setup must stay fast — a JSON-file/SQLite data layer is acceptable for v1)

### 3.2. Non-Functional Requirements
* **Performance:** Dev server startup < 3s; PDF export < 3s; page transitions feel instant.
* **Fast & Flexible Setup:** `npm install && npm run dev` is the entire setup — no DB
  server installation, no environment configuration beyond a single `.env` file.
* **Security:** Admin routes are PIN-gated; PIN attempts are rate-limited; PIN is never
  stored in plain text; submitted data is validated on both client and server.
* **Code Quality:** Strict adherence to clean code principles (see §4).

## 4. Clean Code & Project Structure Rules

### 4.1. Clean Code Principles
* **Single Responsibility:** every component, hook, and module does one thing.
* **Descriptive naming:** `CertificateExportButton`, not `Btn2`.
* **DRY:** shared UI and logic live in `components/ui` and `hooks/`.
* **KISS:** no premature abstraction; prefer plain readable code over clever code.
* **Immutability & pure functions** for business logic (certificate number generation,
  formatting, validation).
* **No dead code, no commented-out code, no magic numbers/strings.**

### 4.2. Hard Constraint: 400 Lines Maximum Per File
> **No file in the project may exceed 400 lines of code.**
> If a file approaches this limit, it MUST be split into smaller, focused modules
> (e.g. extract sub-components, custom hooks, or utility functions).

## 5. Security — 8-Digit PIN Access

* The admin layer is gated by an **8-digit numeric PIN** (e.g. `48291736`) issued by
  the system to authorized clinic staff only.
* Requirements:
  * Exactly **8 digits**, numeric only — enforced on generation and verification.
  * Stored **hashed** (one-way hash + salt), never in plain text.
  * PIN is configurable/regenerable by the system owner.
  * **Rate limiting:** maximum 5 failed attempts, then a lockout cooldown.
  * Failed attempts are logged in the audit trail.
  * Successful unlock grants access to the admin layer for the session only;
    the session expires after a period of inactivity.
  * Admin routes are guarded client-side **and** verified server-side (never rely
    on client-side checks alone).

## 6. PDF Export (Key Feature)

* From the admin history, every application form can be exported as a PDF:
  * **Single export:** download one certificate as `MED-2026-A1B2C3.pdf`.
  * **Bulk export:** select multiple records and export them together.
* PDF layout: official clinic letterhead, applicant details, diagnosis, fit/unfit
  status, recommendations, certificate number, date issued, and signature line.
* Generation happens fast and client-side; output is print-ready (A4, embedded fonts).
